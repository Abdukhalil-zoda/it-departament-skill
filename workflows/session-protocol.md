# Workflow Guide: Session Protocol, Lock & Hand-off

The department rarely runs as a single session. A Cowork orchestrator dispatches waves of sub-agents while
the CTO opens a local CLI session to fix something by hand, a scheduled routine runs the usage audit, and a QA
session drives the device host. All of them read and write one vault. The single-writer rule
([`references/contracts-and-lifecycle.md`](../references/contracts-and-lifecycle.md) §4) already says that only
the coordinator writes shared records; this protocol says **which session** that is, with one hand-written file
and no new runtime: a lock file names the writer, every other session works in contributor mode, and a hand-off
note carries the state from one session to the next.

| Piece | Where | Written by |
| :--- | :--- | :--- |
| **Lock** | `.it-department/lock.json` (git-ignored, shared through the project folder) | the coordinator session that holds it, by hand |
| **Hand-off note** | `.it-department/sessions/_handoff/latest.md` (versioned) + dated copies (git-ignored) | the lock holder at session end; any session may append one `TAKEOVER` or `CONFLICT` line |
| **Transition requests** | `<sessions>/<task-id>/<role>/<session-id>/transition-request.json` | every role; applied by the lock holder with `scripts/apply_transitions.py` |
| **Dashboard** | `<vault>/00-Dashboard.md` | generated by `scripts/dashboard_sync.py`, run by the lock holder |

---

## 1. Session start checklist (coordinator or any role)

1.  **Read `.it-department/config.json`:** `operating_profile` (absent = `production`,
    [`operating-profiles.md`](./operating-profiles.md)), `cto_mode`, `delegated_authorities`.
2.  **Read `<vault>/00-Dashboard.md`:** profile, lock holder, active tasks, open bugs, last usage audit and
    pending CTO decisions.
3.  **Read `.it-department/sessions/_handoff/latest.md`** if present: work in flight, pending transition
    requests, open questions, `TAKEOVER` and `CONFLICT` lines.
4.  **Check the lock** (section 2): take it, renew your own, take over an expired one, or work in contributor
    mode.
5.  **Export nothing yet:** the usage ledger export belongs after each task wave and at session end.

Role sessions (developers, QA, content reviewer, analyst, architect, devops, the usage auditor) never take the
lock: they are contributors by role (section 3). They still run steps 1–4, so they know the profile and who
will apply their transition requests.

**First commands of a new lock holder** (`python` instead of `python3` on Windows):
```bash
python3 <skill_root>/scripts/apply_transitions.py --root <project_root> --dry-run   # requests contributors left since the last writer
python3 <skill_root>/scripts/dashboard_sync.py --root <project_root> --check        # exit 1 = stale dashboard (e.g. a scheduled audit added a report)
```
Apply the requests whose evidence checks out (same command without `--dry-run`) and regenerate a stale
dashboard (without `--check`).

## 2. The lock file: `.it-department/lock.json`

```json
{ "owner_role": "coordinator", "session_id": "<id or free text>", "host": "cowork | cli | <machine>",
  "started_at": "2026-10-07T09:00:00Z", "expires_at": "2026-10-07T13:00:00Z", "scope": "vault + dashboard", "note": "waves 3-4" }
```

| Field | Meaning |
| :--- | :--- |
| `owner_role` | role of the writer, normally `coordinator` |
| `session_id` | the host's session id, or any free text that identifies this session |
| `host` | `cowork`, `cli` or the machine name, so other sessions know where the writer runs |
| `started_at`, `expires_at` | ISO 8601 UTC; default TTL 4 hours |
| `scope` | what the holder writes, normally `vault + dashboard` |
| `note` | what the session is doing, e.g. `waves 3-4` |

| Situation at session start | Action |
| :--- | :--- |
| No `lock.json` | Coordinator: write the lock, then read it back. Role session: contributor mode. |
| Lock with your own `session_id` (a resumed session) | Renew `expires_at` and continue as the writer. |
| Lock expired (`expires_at` in the past) | Append a `TAKEOVER` line to the hand-off note, then write your own lock. |
| Live lock held by another session | Contributor mode (section 3). |
| Lock file not visible (session bound to the git repository only) | Contributor mode: without the project folder you cannot know who writes. |

### Rules
1.  **Single writer.** Only the holder writes shared vault records (task notes and their moves between status
    folders, bug status changes, the decisions journal, ADR status) and the dashboard. Role-owned files stay
    with their roles: QA and the content reviewer create bug notes, the content reviewer owns `06-Content/`,
    every role writes its own reports and session directory.
2.  **Written by hand, no script.** The coordinator writes the file with its file tool; there is no lock
    daemon. Write it, then read it back: if the `session_id` is not yours, another session won the race and
    you work in contributor mode.
3.  **TTL.** Default 4 hours. Renew by rewriting `expires_at` before it passes, for example after every task wave.
4.  **Expired lock.** It may be taken over after appending one line to the hand-off note:
    `- 2026-10-07T13:20:00Z TAKEOVER coordinator@cowork (session s-41, expired 13:00Z) by coordinator@cli (session s-42)`
5.  **Never committed.** The lock is git-ignored (`.it-department/.gitignore`, written by `init-project`) and
    shared through the project folder (a mount or a sync).
6.  **Released at session end** by deleting the file (section 5). An interrupted session's lock simply expires;
    the next coordinator takes it over under rule 4.

## 3. Contributor mode

A session that does not hold the lock (every role session, a second coordinator while the lock is live, a
session that cannot see the lock file) works as a contributor:

| May write | Never writes |
| :--- | :--- |
| its own session directory `<sessions>/<task-id>/<role>/<session-id>/` (deliverables, `handoff.md`, logs) | task notes (frontmatter, moves between status folders) |
| `transition-request.json` for the lock holder to apply | `<vault>/00-Dashboard.md` |
| new bug notes in `<vault>/02-Bugs/` (QA, content reviewer) | the decisions journal, ADR status |
| its own report files in `<vault>/05-Reports/` (usage audit, content review, QA report) and role-owned files (`06-Content/` for the content reviewer) | `lock.json` (except a takeover under section 2) and `latest.md` (except one `TAKEOVER` or `CONFLICT` line) |
| its own usage ledger export | another session's worktree or session directory |

Transition requests are the contributor's voice: the lock holder applies them with `scripts/apply_transitions.py`,
which checks that the note's status still equals `from_status` and refuses stale or illegal requests with a reason.

## 4. Hand-off note: `.it-department/sessions/_handoff/latest.md`

*   Written by the lock holder at session end and read first by the next session. Before overwriting it, keep
    the previous note as `<YYYY-MM-DD>-<session_id>.md` (its own date and session id) in the same folder.
*   `latest.md` is versioned, so a session bound only to the git repository still sees it; the dated copies are
    git-ignored like the lock.
*   Any session may append a single `TAKEOVER` or `CONFLICT` line; nobody else rewrites the note.

```markdown
# Hand-off: {YYYY-MM-DD HH:MM}Z, {owner_role}@{host}, session {session_id}

Profile: {operating_profile} · Lock: released · Usage exported: yes | no

## Done
- {TASK-ID}: {what changed} ({from status} → {to status})

## In flight
| Task | Status | Role | Worktree / branch | Next step |
| :--- | :--- | :--- | :--- | :--- |
| {TASK-ID} | In-Development | backend-dev | `.it-department/worktrees/{TASK-ID}` | {next step} |

## Pending transition requests
- `{sessions}/{TASK-ID}/{role}/{session-id}/transition-request.json`: {why it is not applied yet}

## Open questions for the CTO
- {question} (blocks {TASK-ID} | blocks nothing)

## Next steps
1. {step}

## Log
- {timestamp} TAKEOVER … / CONFLICT …
```

## 5. Session end checklist (lock holder)

1.  **Apply pending transition requests:**
    `python3 <skill_root>/scripts/apply_transitions.py --root <project_root>`; refused requests are listed with
    a reason and go into the hand-off note.
2.  **Regenerate the dashboard:** `python3 <skill_root>/scripts/dashboard_sync.py --root <project_root>`
    (`apply_transitions.py` already runs it unless `--no-sync`; a second run reports `unchanged`).
3.  **Export usage:** `python3 <skill_root>/scripts/usage_ledger.py --root <project_root> --role coordinator`
    (cloud sessions: `--out <staging>` and commit the JSON, [`efficiency-and-usage-audit.md`](./efficiency-and-usage-audit.md) §3.2).
4.  **Write the hand-off note** (section 4), keeping the previous one as a dated copy.
5.  **Release the lock:** delete `.it-department/lock.json`.

Contributors end with their deliverables, `handoff.md` and `transition-request.json` in their session directory,
their usage exported, and their worktree committed or its state described in `handoff.md`.

## 6. Parallel work rules

| Session | Concurrent? | Mode |
| :--- | :--- | :--- |
| Orchestrator (Cowork or CLI) holding the lock | one at a time | writer |
| Developers, each in its own worktree | yes | contributor |
| QA, content reviewer | yes; device runs respect the R5 queue | contributor |
| Scheduled usage audit | yes | contributor (report and sidecar only) |
| A second coordinator, e.g. the CTO's CLI session while Cowork orchestrates | yes | contributor until the lock is free or expired |

*   One writer at a time; any number of contributors. Contributors never share a worktree or a session
    directory, and nobody switches branches in the shared checkout
    ([`orchestration-and-worktrees.md`](./orchestration-and-worktrees.md) §3).
*   **Conflict:** two sessions acting as writer (a race lost to sync delay, a takeover of a lock that was still in
    use) or a shared record changed under a session's feet. The **newer** session (later `started_at`) appends
    one line to the hand-off note and stops touching shared records:
    `- 2026-10-07T10:42:00Z CONFLICT coordinator@cli (session s-42) vs coordinator@cowork (session s-41): both moved ATM-031; stopped writing shared records`
*   The writer (or the CTO) resolves the conflict: `apply_transitions.py --dry-run`, `vault_lint.py` and
    `dashboard_sync.py --check` show the damage, the records are fixed, and the resolution goes into the next
    hand-off note.

---

## 7. Visibility and checks

*   The dashboard header shows the lock: `**Session Lock:** {owner_role}@{host} since {started_at}, expires {expires_at}`
    or `free` (`dashboard_sync.py` reads `lock.json`).
*   `scripts/vault_lint.py` warns when the lock has expired but is still present (`VL014`) and when the
    dashboard is stale (`VL012`).
